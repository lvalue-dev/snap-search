# 경력기술서 — Snap-Search (해외 축구 일정·결과 제공 플랫폼)

## 0. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | Snap-Search (스냅서치) |
| 기간 | 2024.12 ~ 2025.03 |
| 역할 | 백엔드 단독 개발 (설계 · 구현 · 인프라 · 배포 전 영역) |
| 기술 스택 | Java 17, Spring Boot 3.4, Spring Data JPA, Spring Scheduling, WebFlux(WebClient), MySQL 8, Gradle |
| 인프라 | Azure VM 1대(애플리케이션 + MySQL 동거), Azure Blob Storage, Nginx, Docker, GitHub Actions |
| 외부 연동 | api-football(v3) REST API, CSV 기반 초기 적재 데이터 |

**서비스 요약**
시즌 → 국가 → 리그 → 팀으로 좁혀 들어가는 탐색 흐름을 제공하고, 팀 상세(선수단·감독 커리어·다가올 경기)와 경기 상세(개요·이벤트 타임라인)를 제공하는 서비스입니다. 데이터는 **초기 CSV 적재 + 외부 API 증분 배치 갱신**의 2단 구조로 유지합니다.

## 1. 외부 API 호출 한도 제약 하의 데이터 확보 전략

### 문제인식
서비스가 성립하려면 국가·리그·팀·선수·감독·경기 일정/결과 전체가 필요하지만, 사용 중인 api-football은 **무료 플랜 기준 일일 호출 한도**가 있는 유료 API였습니다. 전 시즌 전 리그를 API만으로 채우면 한도를 즉시 소진하고, 그 이후에는 "정작 갱신이 필요한 오늘 경기"를 못 부르는 상황이 발생합니다. 즉 **호출 한도라는 고정 예산을 어디에 쓸 것인가**가 핵심 문제였습니다.

### 방안탐색
1. 전량 API 수집 — 매 조회 시점에 API 호출
2. 전량 정적 데이터 — CSV 덤프만 사용, 갱신 없음
3. **정적 데이터로 과거를 채우고, API 예산은 "변할 수 있는 데이터"에만 사용하는 하이브리드**

### 방안선택 이유
(1)은 한도 소진과 응답 지연을 동시에 야기하고, (2)는 "오늘 경기 결과"라는 서비스의 핵심 가치를 포기하는 선택입니다.
축구 데이터는 **과거 경기 결과는 불변, 미래·진행 중 경기만 가변**이라는 도메인 특성이 뚜렷했습니다. 이 특성을 그대로 저장 전략에 반영하면 API 예산을 "가변 데이터"에만 집중시킬 수 있다고 판단해 (3)을 선택했습니다.

### 조치
- 국가/리그/팀/선수 등 **마스터성 데이터는 CSV 덤프로 선적재**하고, 이후 API 재호출 없이 DB를 정본으로 사용
- 경기 데이터는 **종료 상태가 아닌 건만 갱신 대상으로 식별**하는 쿼리를 작성해, 이미 확정된 경기를 다시 부르지 않도록 차단
  ```sql
  -- 종료(FT)·연기(PST) 상태가 아니면서, 이미 킥오프 시각이 지난 경기만 갱신 대상
  WHERE m.fixtureStatusShort NOT IN ('FT', 'PST') AND m.fixtureDate < :currentDate
  ```
- 마스터 데이터 적재 시 `code + name` 기준 선조회 후 갱신/신규 분기를 넣어, 재실행해도 중복 행이 생기지 않는 **멱등 적재**로 구현

### 회고
"모든 데이터를 실시간으로"가 아니라 **데이터의 변경 주기에 따라 저장 전략을 나누는 것**이 외부 의존 시스템 설계의 출발점이라는 걸 체득했습니다. 갱신 대상 판별을 상태값(`FT`/`PST`)에 의존한 점은 아쉬움이 남습니다. 외부 API의 상태 코드 체계가 바뀌면 조용히 오작동하므로, 상태 코드를 enum으로 내부화하고 매핑되지 않는 코드는 경고 로그를 남기는 방식으로 개선하는 것이 안전합니다.

## 2. 경기 데이터 갱신 배치 — 호출량 제어와 처리 시간의 균형

### 문제인식
경기 결과 갱신은 팀 단위로 fixture를 조회해야 해서 대상 팀 수만큼 API 호출이 발생합니다. 순차 호출은 처리 시간이 팀 수에 정비례해 길어지고, 반대로 전량 병렬 호출은 **외부 API의 초당 요청 제한에 걸려 429 응답**을 유발합니다. "빠르되 상대 서버 제한을 넘지 않는" 지점을 찾아야 했습니다.

### 방안탐색
1. 단순 for-loop 순차 호출
2. 전량 병렬 호출 (`Flux` 무제한 concurrency)
3. **동시성 상한 + 요청 간 간격을 동시에 거는 제어된 병렬 호출**
4. 메시지 큐 도입 후 컨슈머 측에서 유량 제어

### 방안선택 이유
(4)는 VM 1대로 운영되는 현 인프라에 브로커를 추가하는 비용이 효용을 초과했습니다. (2)는 429를 유발해 오히려 재시도 비용이 커집니다.
WebFlux의 `flatMap(mapper, concurrency)`와 `delayElements`를 조합하면 **별도 인프라 없이 동시성과 유량을 코드 레벨에서 함께 제어**할 수 있어 (3)을 선택했습니다.

### 조치
- **동시 호출 5건 상한 + 요청 간 100ms 간격**으로 유량을 고정
  ```java
  Flux.fromIterable(upcomingFixtureIds)
      .delayElements(Duration.ofMillis(100))   // 요청 간 최소 간격 확보
      .flatMap(this::fetchFixtureById, 5)      // 동시 처리 5건으로 상한
      .flatMapSequential(Mono::justOrEmpty)
      .collectList()
      .block();
  ```
- 갱신 대상 리그를 **주요 4개 리그(EPL·리그앙·분데스리가·라리가)로 한정**해 1회 배치의 호출량 자체를 상한선 안으로 설계
- 실행 시점을 **매일 00:15 (Asia/Seoul)** 로 고정 — 유럽 경기 종료 후이면서 트래픽이 가장 낮은 시간대
- 팀 단위 예외를 개별 처리해, **한 팀의 API 실패가 나머지 팀 갱신을 중단시키지 않도록** 격리

### 회고
동시성 5·간격 100ms는 실측 기반이 아니라 보수적 추정으로 정한 값입니다. 지금이라면 429 응답률과 배치 총 소요시간을 지표로 남기고 값을 조정했을 것입니다.
또한 **실패 팀에 대한 재처리 경로가 없다**는 점이 가장 큰 구조적 약점입니다. 실패 건을 별도 테이블에 적재하고 지수 백오프로 재시도하는 보상 트랜잭션이 있어야, "조용히 하루치가 비는" 사고를 막을 수 있습니다.

## 3. 이미지 서버 구축 — 외부 미디어 도메인 의존 제거와 렌더링 최적화

### 문제인식
팀 로고·선수 사진·국기 등 모든 이미지가 외부 미디어 도메인(`media.api-sports.io`)을 직접 참조하고 있었습니다. 이는 세 가지 문제를 동시에 안고 있었습니다.
1. **가용성**: 외부 도메인 장애 시 서비스 화면이 통째로 깨짐
2. **성능**: 목록 화면에서 **35px로 렌더링될 아이콘에 원본 해상도 이미지를 그대로 전송**
3. **통제 불가**: 캐시 정책·Content-Type을 우리가 지정할 수 없음

### 방안탐색
1. 프론트엔드 `<img>` 리사이즈 — 전송량은 그대로, 근본 해결 아님
2. 요청 시점 실시간 리사이즈 프록시 — 첫 요청 지연, VM 1대에 CPU 부담 집중
3. **사전 변환 후 Blob Storage 저장 + 용도별 사이즈 사전 생성**
4. 상용 이미지 CDN 도입 — 비용 발생

### 방안선택 이유
이미지 원본이 **거의 변하지 않는 정적 자산**이라는 점이 결정적이었습니다. 변하지 않는 데이터를 매 요청마다 변환하는 것은 낭비이므로, 배치로 한 번 변환해 저장하는 (3)이 가장 비용 효율적이었습니다. 이미 Azure를 사용 중이라 Blob Storage는 추가 계약 없이 도입 가능했습니다.

### 조치
- 용도별 사이즈를 **사전 생성**하여 디렉터리로 분리 저장
  - 로고/국기: **100×100(상세) / 35×35(목록)**
  - 선수 사진: **150×150(상세) / 80×80(목록)**
  - 저장 경로: `{도메인}/{width}x{height}/{파일명}` → 프론트는 경로 치환만으로 사이즈 선택
- 원본을 **1회만 다운로드해 메모리에 적재**한 뒤, 사이즈별로 스트림을 재생성하여 변환 — 사이즈 수만큼 발생하던 원본 다운로드를 1회로 축소
  ```java
  byte[] originalImageBytes = originalImage.readAllBytes();     // 원본 1회 다운로드
  for (int[] size : sizes) {
      InputStream imageStream = new ByteArrayInputStream(originalImageBytes); // 재사용
      ...
  }
  ```
- 업로드 시 **Content-Type 헤더를 명시 지정**해 브라우저가 올바르게 해석하도록 처리

### 회고
"정적인 자산은 요청 시점이 아니라 사전에 처리한다"는 원칙을 실제 비용 관점에서 이해하게 된 작업입니다.
다만 **파일명이 원본 파일명 그대로**라 원본이 갱신되면 캐시 무효화 수단이 없습니다. 콘텐츠 해시를 파일명에 포함시켰다면 `Cache-Control: immutable`을 안전하게 걸 수 있었을 것입니다. 또한 처리 결과를 최종적으로 WebP로 통일하지 못하고 PNG로 남긴 부분은 전송량 관점에서 개선 여지가 있습니다.

## 4. 이미지 변환 배치의 안전한 점진 실행

### 문제인식
이미 운영 중인 DB의 이미지 URL 전량을 새 경로로 교체해야 했습니다. 전량 일괄 실행 시 **다운로드·리사이즈·업로드가 동시에 몰려 VM 1대의 메모리와 대역폭을 점유**하고, 그 시간 동안 API 응답이 지연됩니다. 또 중간에 실패하면 "일부만 교체된 상태"로 정합성이 깨집니다.

### 방안탐색
1. 전량 일괄 실행
2. 운영자가 수동으로 페이지를 넘기며 실행 (API 트리거)
3. **페이지 단위 자동 점진 실행 + 재실행 안전성 확보**

### 방안선택 이유
(1)은 리소스 스파이크와 부분 실패 위험이 크고, (2)는 사람이 계속 붙어 있어야 합니다.
**작업을 잘게 쪼개 긴 시간에 분산시키면 피크 부하 자체가 사라진다**는 점, 그리고 이 작업이 사용자 대기 시간과 무관한 백그라운드 작업이라 "느려도 되는" 성격이라는 점에서 (3)을 선택했습니다.

### 조치
- **1회 100건(페이지 단위) · 10분 주기 · 기동 후 30초 지연**으로 실행량을 고정해 부하를 시간축으로 분산
- **URL 도메인 판별로 멱등성 확보** — 이미 변환된 건은 건너뛰므로 배치 재기동/중복 실행에도 재변환이 발생하지 않음
  ```java
  private boolean isFromOriginalDomain(String logoUrl) {
      return logoUrl != null && logoUrl.contains("media.api-sports.io");
  }
  ```
- 대상 도메인(리그/팀/선수/국가/감독)별로 배치를 분리하고, **완료된 도메인은 스케줄러에서 비활성화**하는 방식으로 순차 마이그레이션
- 배치 단위로 트랜잭션을 걸어 100건 단위 원자성 확보

### 회고
"별도 처리 이력 테이블 없이, **데이터 자체의 상태(URL 도메인)로 진행 상황을 판별**한다"는 접근은 마이그레이션 성격의 작업에서 매우 유효했습니다. 별도 상태 관리 없이도 재실행 안전성을 얻을 수 있었습니다.
반면 **진행 페이지 번호를 인스턴스 메모리 필드로 관리**한 것은 명백한 설계 실수입니다. 재배포 시 진행 위치가 초기화되고, 인스턴스를 늘리면 중복 처리가 발생합니다. 커서를 DB에 영속화했어야 했습니다. 또한 실행량 제어를 상수로 하드코딩해, 운영 중 조정하려면 재배포가 필요했던 점도 설정 외부화로 개선해야 할 부분입니다.

## 5. 이미지 품질 저하 및 포맷별 변환 오류 대응

### 문제인식
이미지 서버 전환 후, 리사이즈된 팀 로고가 **원본 대비 계단 현상(aliasing)이 눈에 띄게 발생**했고, 국기 이미지는 아예 깨져서 표시되었습니다. 서비스 첫인상을 좌우하는 부분이라 즉시 대응이 필요했습니다.

### 방안탐색
- 품질 문제: (a) 라이브러리(Thumbnailator) 옵션 조정 (b) `Graphics2D` 직접 제어로 렌더링 힌트 지정
- 국기 문제: 원인 분석 결과 **국기가 래스터가 아닌 SVG(벡터) 포맷**이었고, 래스터 리사이즈 파이프라인을 그대로 태워 손상된 것

### 방안선택 이유
품질 문제는 라이브러리 추상화 뒤에서 보간 방식을 정확히 제어할 수 없어, **`Graphics2D`를 직접 다루어 보간·안티앨리어싱·렌더링 우선순위를 명시 지정**하는 방식을 택했습니다.
SVG는 "리사이즈가 필요 없는 포맷"입니다. 벡터는 렌더링 시점에 임의 배율로 확대·축소되므로, **변환하지 않고 원본을 그대로 전달하는 것이 화질·용량·처리비용 모든 면에서 우월**하다고 판단해 파이프라인에서 분기시켰습니다.

### 조치
- 리사이즈 시 **투명도(알파 채널) 보존**을 위해 `TYPE_INT_ARGB` 버퍼를 사용, 로고 배경이 검게 채워지는 문제 차단
- **고품질 렌더링 힌트 3종**을 명시 지정
  ```java
  g2d.setRenderingHint(RenderingHints.KEY_INTERPOLATION, RenderingHints.VALUE_INTERPOLATION_BICUBIC);
  g2d.setRenderingHint(RenderingHints.KEY_ANTIALIASING,  RenderingHints.VALUE_ANTIALIAS_ON);
  g2d.setRenderingHint(RenderingHints.KEY_RENDERING,     RenderingHints.VALUE_RENDER_QUALITY);
  ```
- **Content-Type 기준으로 벡터/래스터 파이프라인 분기** — SVG는 리사이즈를 우회하고 원본을 그대로 업로드
  ```java
  InputStream resizedImage = "image/svg+xml".equals(contentType)
      ? imageStream
      : ImageOptimizationUtil.resizeImage(imageStream, width, height);
  ```

### 회고
이미지 처리에서 **투명도와 보간 방식은 기본값에 맡기면 안 되는 항목**이라는 것을 배웠습니다.
한편 이 분기 로직을 처음 작성할 때 문자열을 `==`로 비교했다가 이후 `equals()`로 수정했습니다. 상수가 좌변이었기에 우연히 동작했을 뿐 **잠재적 결함**이었고, 이후 문자열 조건 분기는 반드시 `equals()`를 좌변 상수 기준으로 쓰는 습관을 들였습니다. 근본적으로는 Content-Type을 문자열이 아닌 enum으로 다뤘어야 할 문제입니다.

## 6. DB 커넥션 단절 대응 — 커넥션 풀 튜닝

### 문제인식
장시간 유휴 상태가 지속되는 새벽 시간대 이후, **배치 실행 시점에 커넥션 관련 오류가 발생**했습니다. 장시간 유휴 커넥션이 서버/네트워크 계층에서 이미 끊겼음에도 풀은 이를 유효한 커넥션으로 간주해 그대로 반환하는 상황이었습니다. 배치가 **하루 한 번 새벽에만 동작**하는 구조라 유휴 구간이 길어 문제가 두드러졌습니다.

### 방안탐색
1. 애플리케이션 레벨 재시도 로직 추가 — 증상만 가림
2. 주기적 keep-alive 쿼리를 직접 구현 — 커넥션 풀이 이미 제공하는 기능의 중복 구현
3. **커넥션 풀(HikariCP) 생명주기 파라미터 튜닝 + JDBC 자동 재연결 설정**

### 방안선택 이유
문제의 본질은 "애플리케이션이 인지하지 못한 죽은 커넥션"이므로, **커넥션의 수명과 유효성 검증을 담당하는 풀 계층에서 해결하는 것이 정확한 위치**였습니다. HikariCP는 keep-alive와 최대 수명 관리를 이미 지원하므로 직접 구현할 이유가 없었습니다.

### 조치
- HikariCP 파라미터를 **유휴 시간이 긴 배치 워크로드에 맞춰 재설정**

  | 항목 | 값 | 의도 |
  | --- | --- | --- |
  | `maximumPoolSize` | 20 | 배치 병렬 처리 + API 트래픽 동시 수용 |
  | `minimumIdle` | 5 | 유휴 시간대에도 최소 커넥션 상시 확보 |
  | `keepaliveTime` | 5분 | **유휴 커넥션을 주기적으로 검증해 단절 감지** |
  | `maxLifetime` | 30분 | DB 측 타임아웃 이전에 선제적으로 커넥션 교체 |
  | `idleTimeout` | 30초 | 불필요한 유휴 커넥션 회수 |
  | `connectionTimeout` | 30초 | 풀 고갈 시 무한 대기 방지 |

- JDBC URL에 `autoReconnect=true`를 추가해 단절 시 재연결 경로 확보
- 동일 설정을 local/prod 프로파일에 함께 적용해 **환경 간 동작 차이를 제거**

### 회고
`maxLifetime`(30분)을 DB 서버의 `wait_timeout`보다 짧게 잡아 **애플리케이션이 먼저 커넥션을 폐기하도록** 만드는 것이 핵심이었습니다. 이 "선제적 교체" 개념은 이후 외부 자원을 다루는 모든 설계에 적용하고 있습니다.
다만 각 수치를 DB 서버의 실제 타임아웃 설정을 확인하고 역산한 것이 아니라 통용되는 권장값을 참고해 정한 점, 그리고 커넥션 풀 지표를 모니터링하지 않아 **문제 해결을 로그 부재로만 확인**한 점은 한계입니다. Actuator로 풀 사용률을 노출했다면 설정의 타당성을 데이터로 검증할 수 있었습니다.

## 7. 경기 이벤트 데이터 정합성 — PK 충돌과 Null 처리

### 문제인식
경기 상세의 타임라인(득점·교체·카드)을 저장하는 과정에서, 한 경기(fixture)에 여러 이벤트가 존재함에도 **fixture ID를 PK로 사용해 이벤트가 서로 덮어쓰기**되는 문제가 있었습니다. 또한 외부 API 응답에서 **어시스트·연장시간·경기 상태 등 상당수 필드가 상황에 따라 null로 내려와** 원시 타입(primitive) 매핑 시 역직렬화 단계에서 실패했습니다.

### 방안탐색
- PK: (a) fixture ID + 경과시간 복합키 (b) 대리키(surrogate key) 도입
- Null: (a) 응답 수신 후 기본값 치환 (b) 래퍼 타입으로 전환해 null을 그대로 수용

### 방안선택 이유
복합키는 "같은 시간에 여러 이벤트가 발생"하는 축구 도메인에서 유일성을 보장하지 못합니다(동시 교체 등). 도메인상 자연키가 존재하지 않으므로 **대리키가 정답**이었습니다.
Null 처리에서는 기본값 치환(예: 어시스트 없음 → 0)이 **"어시스트가 0번 선수"라는 잘못된 의미를 만들어냅니다.** "값이 없음"과 "값이 0"은 다른 정보이므로, 이를 구분해 보존하는 래퍼 타입 전환을 선택했습니다.

### 조치
- 이벤트 엔티티에 `@GeneratedValue(strategy = IDENTITY)` 기반 **대리키를 도입**하고, fixture ID는 조회용 일반 컬럼으로 전환
- 어시스트 ID, 연장 시간, 경기 상태 등 **선택적 필드를 전부 래퍼 타입으로 전환**해 null을 손실 없이 보존
- 경기 시각은 **모두 UTC로 정규화해 저장**하고, 조회 시 KST로 변환 — 시간대 혼재로 인한 "다가올 경기" 오판 방지
- 타임라인 조회는 경과 시간 오름차순 정렬을 쿼리에 위임해 애플리케이션 정렬 부하 제거

### 회고
**"자연키처럼 보이는 값이 실제로 유일한가"를 도메인 관점에서 검증하는 절차**가 스키마 설계에 반드시 필요하다는 것을 배운 사례입니다.
아쉬운 점은 감독 커리어 데이터를 CSV 원본 구조 그대로 **커리어 항목이 컬럼으로 나열된 와이드 테이블**로 받아, 조회 시 컬럼을 순회 파싱하는 코드가 되었다는 것입니다. 정규화된 자식 테이블로 옮겼다면 조회 로직이 훨씬 단순해졌을 것이며, 현재 구조는 커리어 개수 상한에 종속되는 문제도 있습니다.

## 8. 배포 자동화 파이프라인 구축

### 문제인식
매 배포마다 로컬 빌드 → 산출물 전송 → 서버 접속 → 컨테이너 재기동을 수동으로 수행하고 있었습니다. 절차가 길어 실수 여지가 크고, **로컬 환경 차이에 따라 산출물이 달라질 위험**이 있었습니다. 또한 Azure Blob 연결 문자열 등 자격 증명이 빌드 시점에 주입되어야 했습니다.

### 방안탐색
1. 배포 스크립트만 작성해 수동 실행
2. **GitHub Actions + Docker 기반 자동화**
3. 별도 CI 서버(Jenkins 등) 구축

### 방안선택 이유
(3)은 VM 1대 환경에 CI 서버를 얹는 것이 자원상 불가능했습니다.
(2)는 저장소에 이미 GitHub를 쓰고 있어 추가 인프라가 0이며, **멀티스테이지 Docker 빌드로 "빌드 환경까지 코드로 고정"** 할 수 있어 로컬 환경 차이 문제를 근본적으로 제거합니다.

### 조치
- **main 브랜치 push를 트리거**로 빌드 → 이미지 생성 → 레지스트리 push까지 자동화
- **멀티스테이지 Dockerfile** 적용 — 빌드는 Gradle+JDK 이미지에서, 실행은 JDK slim 이미지로 분리해 최종 이미지에서 빌드 툴체인 제거
  ```dockerfile
  FROM gradle:8.11.1-jdk17 AS build
  RUN ./gradlew clean build -x test --no-daemon
  FROM openjdk:17-jdk-slim
  COPY --from=build /app/build/libs/*.jar app.jar
  ```
- 자격 증명은 저장소에 두지 않고 **GitHub Secrets에서 빌드 시점 주입**
- 배포 대상 VM이 **애플리케이션과 MySQL을 함께 구동**하는 단일 서버라, 무중지 배포용 SSH 자동 배포 단계는 파이프라인에서 분리하고 이미지 배포까지를 자동화 범위로 확정

### 회고
"이미지 push까지 자동화하고 실제 배포는 수동"이라는 절충은 인프라 제약을 고려한 현실적 선택이었지만, **자동화의 마지막 한 단계가 비어 있으면 파이프라인의 효용이 절반**이 됩니다. 헬스체크 기반 롤링 배포를 붙이는 것이 다음 과제입니다.
또한 배포 파이프라인에서 **테스트 단계를 건너뛰도록(`-x test`) 구성**한 점이 가장 큰 부채입니다. 외부 API·Blob Storage 의존성 때문에 테스트 작성이 어려웠던 것이 원인인데, 이는 곧 **의존성을 인터페이스로 분리하지 않은 설계 문제**이기도 합니다. 실제로 `AzureBlobService`만 인터페이스/구현으로 분리해두었으나 테스트 대역을 활용하는 데까지 나아가지 못했습니다.

## 9. 종합 회고

### 잘한 점
- **도메인 특성을 저장 전략으로 번역했습니다.** "과거 경기는 불변"이라는 성질을 정적 적재 + 증분 갱신 구조로 옮겨, 제한된 API 예산 안에서 서비스가 성립하도록 만들었습니다.
- **제약을 설계의 입력으로 다뤘습니다.** VM 1대·무료 API 티어라는 조건에서 브로커나 CI 서버를 추가하는 대신, 유량 제어와 점진 배치로 같은 목표를 달성했습니다.
- **재실행 안전성을 데이터 자체로 확보했습니다.** URL 도메인 판별과 선조회 후 분기로 별도 상태 테이블 없이 멱등성을 얻었습니다.

### 부족했던 점과 개선 방향
| 항목 | 문제 | 개선 방향 |
| --- | --- | --- |
| 자격 증명 관리 | DB 접속 정보가 프로파일 파일에 평문으로 포함 | 전량 환경변수/Secret 주입으로 전환하고 노출된 자격 증명 교체 |
| 스키마 관리 | `ddl-auto=update`로 운영 스키마를 ORM에 위임 | Flyway 등 마이그레이션 도구로 스키마 변경 이력 관리 |
| 배치 상태 관리 | 진행 페이지를 인스턴스 메모리에 보관 | 커서를 DB에 영속화 |
| 실패 처리 | 배치 실패 건에 대한 재처리 경로 부재 | 실패 이력 적재 + 지수 백오프 재시도 |
| 관측 가능성 | 표준 출력 로그 위주, 지표 부재 | 로거 일원화, Actuator로 커넥션 풀·배치 소요시간 노출 |
| 테스트 | 외부 의존성 결합으로 테스트 미작성 | 외부 연동을 포트로 분리하고 테스트 대역 적용 |
| 보안 설정 | CORS가 모든 오리진 허용 + 인증정보 허용 | 오리진 화이트리스트로 축소 |

### 다음에 적용할 원칙
1. **성능·안정성 판단은 지표로 검증한다.** 동시성·풀 크기 같은 수치를 권장값이 아닌 측정값 기반으로 정하고, 그 근거를 남깁니다.
2. **테스트 가능성은 설계 품질의 지표다.** 테스트가 어렵다면 그것은 테스트의 문제가 아니라 의존성 분리가 안 된 설계의 신호입니다.
3. **외부 시스템은 반드시 실패한다고 가정한다.** 실패 격리뿐 아니라 재처리 경로까지 포함해야 배치가 완성됩니다.
